# 효도여행 설계 도우미

자녀가 화면 몇 장에 조건을 넣으면 서버가 동선을 계산하고, 부모님께는 큰 글씨 한 장 일정표로 전달합니다.
지금은 **모바일 웹사이트**로 동작하고, 나중에 같은 코드를 앱(Capacitor)으로 감쌀 수 있게 만들었습니다.

## 빠르게 실행

```bash
npm install
npm run dev          # 서버 http://localhost:8787 + 화면 http://localhost:5173
```

API 키가 없어도 바로 돌아갑니다. 키가 없는 단계는 **예시 데이터(서울 중구 일대)·직선거리 추정**으로 대신하고,
화면 ④ 맨 위에 그렇다고 표시합니다. 실제 데이터로 바꾸려면:

```bash
cp .env.example .env   # 키를 채운 뒤 npm run dev 다시 실행
```

| 명령 | 하는 일 |
| --- | --- |
| `npm run dev` | 개발 모드 (서버 + Vite) |
| `npm run build && npm start` | 화면을 빌드해 서버 하나로 제공 (http://localhost:8787) |
| `npm run build:demo` | 서버 없이 브라우저에서 예시 데이터로 도는 한 파일짜리 데모 → `client/dist-demo/index.html` |
| `npm test` | 일정 엔진·API 응답 파싱 테스트 (63개) |
| `npm run eval:recommend` | 취향 추천 방식 비교 평가 → `eval/results.md` (키 불필요, 첫 실행 때 모델 내려받기) |
| `npm run typecheck` | 타입 검사 |

`?flow=mvp` 를 주소 뒤에 붙이면 **해커톤 MVP 흐름(① → ② → ④)**, 붙이지 않으면 **학술대회 버전(① ~ ⑤)** 입니다.

### 서버가 하는 6단계 (`core/src/planner.ts`)

| 단계 | 키가 있을 때 | 키가 없을 때 |
| --- | --- | --- |
| 1 후보 수집 | TourAPI `KorService2/areaBasedList2`(법정동 코드) + `locationBasedList2` (관광지 12·문화시설 14·음식점 39) | 예시 데이터 |
| 2 접근성 필터 | 무장애 여행 정보 `KorWithService2/areaBasedList2`(법정동 코드) + `detailWithTour2` | 예시 데이터 |
| 3 이동 시간 계산 | 카카오맵 도보 경로 `GET /v2/routing/walk` (`route_mode=ACCESSIBLE`, 편안한 길) · 카카오모빌리티 `GET /v1/directions` | 직선거리 × 보정계수 |
| 4 순서 최적화 | 우리 코드: 하루 방문지(최대 7곳)의 모든 순서를 비교 | 같음 |
| 5 쉬는 곳 채우기 | 카카오 로컬 카테고리 검색 `CE7`(카페) | 예시 카페 |
| 6 설명 붙이기 | LLM (Anthropic 또는 OpenAI 호환) | 템플릿 문장 |

이동 시간과 순서는 코드가 계산하고, LLM은 문장만 씁니다. LLM 문장에 계산 결과에 없는 숫자가 나오면 버리고 템플릿을 씁니다
(`explanationIsGrounded`). 결과 화면 아래 **서버가 한 일 (6단계)** 에서 단계별 소요 시간·API 호출 수·데이터 출처를 볼 수 있어
발표의 정량 평가 자료로 쓸 수 있습니다.

### 일정 계산 규칙 (튜닝은 `core/src/config.ts`)

- 후보 반경: 화면 ①에서 동네 2km · 보통 3km · 넓게 5km (지역 중심에서 직선거리). 조건·취향·휴무로 거른 뒤
  관광지가 8곳 미만이거나 식당이 3곳 미만이면 반경을 2배씩 최대 2번 넓혀 다시 찾고(20km까지) 결과에 안내합니다.
  화면 ④에서 빼기·바꾸기를 할 때는 처음 결과가 쓴 반경을 그대로 씁니다.
- 도심처럼 후보가 많은 곳은 가까운 순 관광지 150곳·음식점 200곳까지만 보므로 5km를 골라도 실제로는 가까운 곳 위주로 짜입니다.
- 같은 중분류(시장·시장, 고궁·고궁)가 하루에 겹치면 덜 고르고, 같은 궁·절 이름을 품은 가까운 곳(덕수궁 돌담길·대한문·미술관 덕수궁)은 한 곳으로 봅니다.

- 체류: 관광지 60분, 식사 60분, 휴식 20분 ('구경하며 쉬기'를 고르면 30분 + 관광지 1곳 줄임)
- 걷는 시간 × 1.3 ('천천히'), 보행 한도를 넘는 구간은 택시 (호출 대기 3분 포함)
- 다음 방문까지 활동 시간이 '쉬는 간격'을 넘으면 그 전에 근처 카페 휴식. 식사는 휴식으로 침
- 식당에 일찍 도착하게 되면 앞 장소에서 더 머물다 출발
- 하루 관광지 수는 시간 예산으로 정하고, 끝나는 시각을 넘기면 점수가 낮은 곳부터 빼고, 시간이 많이 남으면 근처 한 곳을 더함
- 비용 = 이동 시간 + 걷는 시간×0.2 + 식사 전 대기×0.3 + 늦은 식사×2 + 종료 초과×10
- TourAPI '매주 ○요일' 휴무 안내가 여행 요일과 겹치면 후보에서 뺌. 이름에 '(5, 10일)'처럼 장날이 적힌 5일장은 장날에만 넣음

### 취향 항목 (화면 ③, `core/src/prefs.ts`)

| 그룹 | 항목 | 매칭 |
| --- | --- | --- |
| 음식 | 한식·국밥·면·해산물·중식·일식·양식 | 이름·메뉴 키워드 + 신분류(FD01·FD0201·FD0202·FD0203) |
| 관심사 | 궁궐·미술관·한옥·공원·**시장·바다·사찰·전통체험·온천** | 신분류(SH06 시장, NA0205·0207~0209 바다, HS0301·EX0401·EX0402 사찰, EX01·EX02 체험, EX0501 온천) + 이름 |
| 하고 싶은 것 | 구경하며 쉬기·사진·**산책·맛집 탐방·쇼핑·공연 관람** | 산책 VE03·NA0407·VE0401·VE0403 / 쇼핑 SH01·SH02·SH0501·SH0503·SH06 / 공연 VE0601(영화관 VE0602는 제외) |

- 시장·쇼핑을 고를 때만 쇼핑(38) 목록을 받고, 그중 시장·백화점·복합쇼핑몰·아웃렛·공방·기념품점만 남깁니다 (서울 중구 38은 552곳 중 대부분이 개별 면세점 매장).
- 맛집 탐방: 관광공사에 사진과 대표 메뉴가 함께 등록된 식당에 가산점, 식당 거리 감점을 절반으로.
- 공연 관람: 공연장을 후보에 넣되 일정표 시간은 60분 둘러보기 기준이라 공연 시간을 확인하라고 안내합니다.
- **기타** 직접 입력: 쉼표로 여러 개. 목록 항목이나 별칭(바닷가→바다, 절→사찰, 회→해산물 …)이면 그 항목으로, 아니면 장소 이름·메뉴 키워드로 찾고,
  반경 안에 맞는 곳이 하나도 없으면 결과에 알려 줍니다.

### 의미 기반 추천 — 문장 임베딩 모델 + BM25 (`core/src/semantic.ts`, `server/src/providers/semantic.ts`)

키워드 규칙은 이름·메뉴에 그 낱말이 있어야만 찾습니다 ('성당'을 적으면 이름에 '성당'이 든 곳만).
문장 임베딩 모델은 문장을 벡터로 바꿔 **뜻이 가까운지** 봅니다 — "전통 술 빚기" ↔ "모주 만들기 원데이클래스".

- 모델: [`Xenova/multilingual-e5-small`](https://huggingface.co/Xenova/multilingual-e5-small) (intfloat/multilingual-e5-small 의 ONNX 판, 한국어 포함 다국어).
  [transformers.js](https://huggingface.co/docs/transformers.js)로 **서버 CPU에서 직접 실행**하므로 API 키가 필요 없습니다.
  서버가 켜질 때 불러 두고, 처음이면 Hugging Face 에서 한 번 내려받아 `server/.cache/models` 에 둡니다.
- 장소 문장: 이름 + TourAPI 신분류 이름(`lclsSystmCode2`, 예: 역사관광 > 종교성지 > 불교) + 소개글(`detailCommon2` overview 앞 300자).
  소개글과 벡터는 `server/.cache` 에 저장해 같은 장소는 다시 받거나 계산하지 않습니다.
- 질의: 고른 취향마다 설명 문장 하나(궁궐 → "조선 왕실의 궁궐과 고궁"), 기타 입력, 자유 입력.
  **부정문**("시끄러운 곳은 싫어")은 임베딩이 오히려 시끄러운 곳을 가깝게 볼 수 있어 질의에 넣지 않고 규칙(피하기)으로만 씁니다.
- 점수: 질의마다 [임베딩 코사인 유사도]와 [BM25(소개글 키워드)]를 후보 안에서 표준화(z)해 평균 → 질의들 중 최댓값.
  취향을 고르면 관광지 후보를 40곳까지 두고 이 점수를 다시 표준화해 `0.4 × z`(−0.6 ~ +0.8)를 규칙 점수에 더합니다.
  z ≥ 1 이면 타임라인에 '추천 이유 · 소개글이 취향과 비슷'으로 보입니다.
- 모델이 아직 준비 중(첫 내려받기)이거나 못 쓰는 환경이면 BM25 만으로 의미 점수를 냅니다. 결과 화면 '서버가 한 일'에 실제로 쓴 방식이 나옵니다.
- 끄기: `.env` 에 `EMBEDDING_MODEL=off`. onnxruntime-node 는 macOS(Apple Silicon)·Windows·Linux 를 지원하고 Intel Mac 은 지원하지 않아 BM25 만 씁니다.

**평가** ([eval/README.md](eval/README.md), [eval/results.md](eval/results.md)) — TourAPI 실제 후보(서울 시청 주변 80곳, 전주 한옥마을 주변 80곳)와 질의 24개.
정답 라벨은 Claude 가 초안으로 붙였으니 발표 전에 팀이 검토해 주세요.

| 방식 | P@5 | R@10 | nDCG@10 | MRR |
| --- | --- | --- | --- | --- |
| 이름 키워드 (지금 방식) | 0.208 | 0.326 | 0.335 | 0.533 |
| BM25 (소개글 포함 키워드) | 0.500 | 0.741 | 0.716 | 0.827 |
| 문장 임베딩 | 0.533 | 0.828 | 0.778 | 0.910 |
| **BM25 + 임베딩 (앱이 쓰는 방식)** | **0.575** | **0.861** | **0.821** | **0.911** |

질의별 nDCG@10 으로 보면 임베딩은 이름 키워드보다 22번 낫고 2번 못했고, BM25+임베딩은 BM25 단독보다 15번 낫고 8번 같고 1번 못했습니다.
임베딩 단독과 BM25 단독은 11승 2무 11패로 비슷해, 둘을 합쳐 쓰는 쪽을 앱에 넣었습니다.

### 여러 날 일정 (화면 ① 여행 기간, `core/src/multiday.ts`)

- 1일차: 출발 장소 → … → 숙소 / 가운데 날: 숙소 → … → 숙소 / 마지막 날: 숙소 → … → 출발 장소(돌아오기를 골랐을 때). 하루 일정 시간은 날마다 같습니다.
- 앞선 날에 간 관광지·식당·휴식 카페는 다음 날 후보에서 빼고, 바꾸기 후보에서도 다른 날에 들어간 곳은 뺍니다.
- 숙소를 직접 정하지 않으면 TourAPI 숙박(32)에서 추천: 지역 중심에서 가깝고, 호텔·콘도·레지던스·한옥스테이 우선, 체크한 시설(엘리베이터·주차)이
  없다고 명시된 곳 제외, 캠핑·유스호스텔·게스트하우스 제외. 숙소의 시설 정보가 없으면 예약 전에 확인하라고 안내합니다.
- 숙소 바꾸기는 다니는 곳을 그대로 두고 순서·이동만 새 숙소 기준으로 다시 계산합니다. 한 장 일정표는 날짜별로 나눠 한 장에 담습니다.

| `ANTHROPIC_API_KEY` 또는 `OPENAI_API_KEY`+`OPENAI_MODEL` | 각 콘솔 | 없으면 템플릿 |

API 호출을 줄이려고 서버 메모리에 캐시합니다 (목록 6시간, 상세·무장애 24시간, 경로 1시간).
도보 경로는 A→B와 B→A를 같다고 보고 한 번만 부르고, 자동차 경로는 도보가 보행 한도를 넘는 구간에만 부릅니다.

## 카카오톡으로 보내기 (F5)

1. 휴대폰에서는 Web Share API로 **사진 파일**을 공유 시트에 넘깁니다 → 카카오톡을 고르면 부모님은 사진 한 장을 받습니다 (키 필요 없음).
2. 그게 안 되는 환경(대부분의 PC)에서 `VITE_KAKAO_JS_KEY` 가 있으면 `Kakao.Share.uploadImage` → `sendDefault`(피드)로 보냅니다.
3. 둘 다 안 되면 이미지를 저장하고 안내 문구를 띄웁니다.

기획안의 "서버가 이미지·PDF로 만듭니다"는 브라우저에서 만드는 방식으로 구현했습니다 (`html-to-image`, `jspdf`). 서버 비용이 들지 않고 결과는 같습니다.

## 앱으로 만들 때 (Capacitor)

```bash
cd client
npm i @capacitor/core @capacitor/cli @capacitor/android @capacitor/ios
npx cap init "효도여행" kr.hyodo.trip --web-dir dist
# .env 에 VITE_API_BASE=https://배포한-서버-주소  를 넣고
npm run build && npx cap add android && npx cap sync
```

- 서버는 그대로 배포하고, 앱은 `VITE_API_BASE` 로 그 서버를 부릅니다. 서버 `.env` 의 `CORS_ORIGINS` 에 앱 Origin(`capacitor://localhost`, `https://localhost` 등)을 넣으세요.
- API 키는 전부 서버에만 있습니다. 카카오 JS 키만 화면에 들어가며, 앱에서 카카오 지도·공유를 쓰려면 카카오 디벨로퍼스에 앱 플랫폼 정보를 따로 등록해야 합니다.

## TourAPI 사용 시 주의 (2026-11 실제 응답으로 확인)

- `locationBasedList2`(좌표 반경)와 `areaBasedList2`(`areaCode`)는 **옛 지역코드(areacode)가 남아 있는 일부 장소만** 돌려줍니다.
  명동 반경 3km 관광지가 3곳만 나오고 덕수궁·명동성당·남산골한옥마을이 빠졌습니다 (키워드 검색과 상세 조회로는 정상 조회됨).
- 새 법정동 코드로 조회해야 전부 나옵니다: `areaBasedList2?lDongRegnCd=11&lDongSignguCd=140` → 서울 중구 관광지 70곳.
  무장애 여행 정보(`KorWithService2`)도 같습니다 (위치기반 4곳 → 법정동 기준 168곳).
- 그래서 서버는 반경 중심과 둘레 8곳의 법정동 코드를 카카오 `coord2regioncode`로 구해(앞 2자리 = `lDongRegnCd`, 다음 3자리 = `lDongSignguCd`)
  시군구별 목록을 받은 뒤 좌표로 반경 안만 남깁니다 (`server/src/providers/tourApi.ts`).
- 취향·분류 매칭은 `lclsSystmCode2`로 확인한 신분류 코드를 씁니다 (`core/src/prefs.ts` 맨 위 주석).
  교통시설(VE11)·공연시설(VE06, '공연 관람'을 고르면 공연장 VE0601만 허용)·주점(FD04)·카페(FD05) 등은 후보에서 뺍니다.
- 관광타입 확인: 체험(EX)·사찰(HS0301)은 관광지(12), 공연장(VE0601)은 대부분 문화시설(14), 시장(SH06)은 쇼핑(38)으로 등록돼 있습니다.
