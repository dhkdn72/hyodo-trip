# 취향 추천 평가

같은 질의·같은 후보로 장소 추천 방식 네 가지를 비교합니다. 결과는 [results.md](results.md).

```bash
npm run eval:recommend      # API 키 불필요. 처음 한 번 임베딩 모델을 내려받음
```

## 데이터 (`data/*.json`)

- 한국관광공사 TourAPI(KorService2) 실제 응답, 2026-11-26 수집.
- 지역 중심에서 반경 3km 안의 관광지·문화시설·쇼핑 후보를 **앱과 같은 기준**으로 거른 뒤(교통시설·공연장·숙박 제외, 쇼핑은 시장·백화점 등만) 가까운 80곳.
  - `seoul-center`: 서울시청(37.5663, 126.9779) 주변 80곳
  - `jeonju`: 전주 한옥마을(35.8151, 127.1530) 주변 80곳
- 각 장소: 이름, 신분류 이름(`lclsSystmCode2`), 소개글(`detailCommon2` overview 앞 400자). 모델은 이 중 앞 300자를 봅니다(앱과 같음).
- 다시 만들기: `npm run dev` 상태에서 `GET /api/dev/eval-dump?name=jeonju&lat=35.8151&lng=127.1530&radius=3000&max=80`

## 질의와 정답 (`queries.json`)

- 질의 24개 (서울 12, 전주 12). 부모님 여행에서 나올 만한 취향을 '기타'·자유 입력처럼 적었습니다.
  장소 이름을 그대로 옮긴 질의(키워드에 유리)와 다른 말로 바꾼 질의(예: "옛날 돈과 은행 이야기" → 화폐박물관)를 섞었습니다.
- 정답 기준: 그 질의를 말한 사람에게 **추천해도 될 곳**이면 정답(1), 아니면 0. 이름·분류·소개글에 근거하고,
  소개글에 없더라도 널리 알려진 사실(예: 서울시립미술관 서소문본관은 옛 대법원 건물)은 반영했습니다.
- **정답 라벨은 Claude 가 위 데이터를 읽고 초안으로 붙였습니다.** 발표에 쓰기 전에 팀이 `relevantNames` 를 훑어보고 고쳐 주세요
  (고친 뒤 `npm run eval:recommend` 를 다시 실행하면 결과가 갱신됩니다).

## 비교 방식

| 방식 | 내용 |
| --- | --- |
| 이름 키워드 (지금 방식) | 질의를 낱말(두 글자 이상)로 나눠 장소 **이름**에 들어 있는 낱말 수. 앱의 '기타' 입력 매칭과 같은 성격 |
| BM25 | 이름 + 분류 + 소개글을 글자 2개씩(bigram) 끊어 BM25 — 소개글까지 보는 강한 키워드 기준선 |
| 문장 임베딩 | `Xenova/multilingual-e5-small` 코사인 유사도 (`query: ` / `passage: ` 접두어) — 앱과 같은 모델·같은 장소 문장 |
| BM25 + 임베딩 | 두 점수를 질의별로 표준화(z)해 평균 — **앱이 쓰는 방식** (`server/src/providers/semantic.ts`) |

점수가 같으면 지역 중심에서 가까운 순으로 줄 세웁니다.

## 지표

- **P@5**: 위 5곳 중 정답 비율 — 화면에 보이는 추천이 맞는지
- **R@10**: 정답 중 위 10곳 안에 든 비율
- **nDCG@10**: 정답이 위에 있을수록 높음 (1이 최고)
- **MRR**: 첫 정답 순위의 역수 평균

## 한계
