# 효도여행 설계 도우미 — AI 차별성

> **"부모님 취향을 문장으로 말하면, AI가 뜻을 이해해 장소를 고르고, 계산 엔진이 부모님 체력에 맞는 동선을 짠다."**

---

## 1. 풀려는 문제

부모님 여행 취향은 "조용히 걷기 좋은 곳", "옛날 건물 좋아하셔", "전통 술 빚는 거 해 보고 싶어 하셔"처럼 **문장**으로 나옵니다.
그런데 장소 이름에서 낱말을 찾는 **키워드 방식**은 이런 문장을 잘 다루지 못합니다.

| 부모님 취향 | 키워드 방식의 한계 |
| --- | --- |
| "전통 술 빚기" | '모주 만들기 공방'의 이름에는 '술'이 없어 못 찾음 |
| "옛날 돈과 은행 이야기" | '화폐박물관'은 찾아도 '금융사박물관'은 놓침 |
| "서울의 옛 모습" | 이름에 '서울'이 든 도서관·광장이 상위에 섞여 나옴 |

이 앱은 **AI로 문장의 뜻을 이해해** 이 문제를 풉니다.

---

## 2. AI가 하는 일

```
 부모님 취향 (고른 항목 · 기타 입력 · 자유 입력)
        │
        ▼
 ① 의미 기반 추천 ─ 문장 임베딩 모델 + BM25        ← 핵심 AI (키 없이 서버에서 실행)
        │   취향 문장 ↔ 관광공사 장소 소개글의 '뜻' 비교
        ▼
 ② 조건 해석 ─ LLM (자유 입력 → 피할 곳·좋아할 곳)  ← LLM 키가 있을 때 (없으면 규칙)
        │
        ▼
 동선 계산 엔진 ─ 보행 한도·휴식·식사·택시 전환·순서 최적화  ← AI 아님, 결정적 계산
        │
        ▼
 ③ 설명 생성 ─ LLM이 계산 결과를 문장으로 (숫자 검증)   ← LLM 키가 있을 때 (없으면 템플릿)
```

### ① 의미 기반 추천 — 핵심 차별점

| 항목 | 내용 |
| --- | --- |
| 모델 | `Xenova/multilingual-e5-small` (intfloat/multilingual-e5-small 의 ONNX 판, 한국어 포함 다국어, 384차원) |
| 실행 | transformers.js 로 **우리 서버 CPU에서 직접 실행** — 외부 AI API·키·사용료 없음, 모델 파일(양자화 118MB)은 처음 한 번만 내려받음 |
| 장소 문장 | 이름 + 관광공사 신분류 이름(예: 역사관광 > 종교성지 > 불교) + 소개글 앞 300자 |
| 질의 | 고른 취향마다 설명 문장(궁궐 → "조선 왕실의 궁궐과 고궁"), 기타 입력, 자유 입력 |
| 점수 | 질의별로 [임베딩 유사도]와 [BM25 소개글 키워드 점수]를 표준화해 평균 → 질의 중 최댓값 → 기존 규칙 점수에 가산 |
| 화면 | 일정 카드에 **"추천 이유 · 소개글이 취향과 비슷"** 표시, '서버가 한 일'에 쓴 모델 표시 |

**설계에서 신경 쓴 점**

- **부정문 처리** — "시끄러운 곳은 싫어"를 임베딩에 넣으면 오히려 시끄러운 곳이 가깝게 나올 수 있습니다.
  부정 표현이 있는 문장은 임베딩 질의에서 빼고, 규칙(피하기)으로만 처리합니다.
- **하이브리드** — 임베딩만 쓰지 않고 소개글 키워드(BM25)와 합쳤습니다. 평가에서 둘을 합친 쪽이 가장 좋았습니다(3장).
- **질의별 표준화** — 질의마다 유사도 크기가 달라 한 취향이 점수를 독차지하지 않도록, 질의별로 표준화한 뒤 합칩니다.
- **끊김 없는 대체** — 모델을 내려받는 중이거나 쓸 수 없는 환경(예: Intel Mac)이면 BM25 만으로 계속 동작합니다.

### ② 조건 해석 · ③ 설명 생성 — LLM (선택)

- 자유 입력("계단 많은 곳은 힘들어하세요")을 LLM이 `피할 곳 / 좋아할 곳 / 피할 음식 / 좋아할 음식` 조건으로 바꿉니다.
- 일정 설명은 LLM이 쓰되, **계산 결과에 없는 숫자가 하나라도 나오면 버리고 템플릿 문장을 씁니다** (`explanationIsGrounded`).
- LLM 키가 없으면 규칙·템플릿으로 동작합니다. ①은 LLM 키 없이 관광공사 키만 있으면 동작합니다.

### AI와 계산의 역할 분담

| AI가 맡는 것 | 계산 엔진이 맡는 것 |
| --- | --- |
| 취향 문장의 뜻 이해, 장소 고르기 | 걷는 시간('천천히'면 ×1.3), 보행 한도 넘으면 택시, 휴식·식사 시각 |
| 자유 입력 해석 | 방문 순서 최적화(모든 순서 비교) |
| 설명 문장 | 시간·거리·요금 숫자 |

시간·거리 같은 **숫자는 AI가 만들지 않습니다.** 부모님 일정에서 틀리면 안 되는 부분은 결정적 계산으로, 사람의 말을 이해해야 하는 부분은 AI로 나눴습니다.

## 3. 정량 평가

같은 질의·같은 후보로 네 가지 방식을 비교했습니다 (`npm run eval:recommend`, 자세한 결과 `eval/results.md`).

- **데이터**: 한국관광공사 TourAPI 실제 후보 160곳 — 서울 시청 주변 80곳, 전주 한옥마을 주변 80곳 (2026-11-26 수집)
- **질의**: 부모님 취향 문장 24개 (서울 12, 전주 12)
- **지표**: P@5(위 5곳 중 정답 비율), R@10, nDCG@10(정답이 위에 있을수록 높음), MRR(첫 정답 순위)

| 방식 | P@5 | R@10 | nDCG@10 | MRR |
| --- | --- | --- | --- | --- |
| 이름 키워드 (기존 방식) | 0.208 | 0.326 | 0.335 | 0.533 |
| BM25 (소개글 키워드) | 0.500 | 0.741 | 0.716 | 0.827 |
| 문장 임베딩 | 0.533 | 0.828 | 0.778 | 0.910 |
| **BM25 + 임베딩 (앱 적용)** | **0.575** | **0.861** | **0.821** | **0.911** |

질의별 nDCG@10 비교 (승·무·패)

| 비교 | 승 | 무 | 패 |
| --- | --- | --- | --- |
| 임베딩 vs 이름 키워드 | 22 | 0 | 2 |
| 임베딩 vs BM25 | 11 | 2 | 11 |
| BM25 + 임베딩 vs BM25 | 15 | 8 | 1 |
| BM25 + 임베딩 vs 임베딩 | 13 | 2 | 9 |

**해석**

- 기존 이름 키워드 방식 대비 nDCG@10 **0.335 → 0.821 (약 2.5배)**, 위 5곳 정답 비율 **0.208 → 0.575**.
- 임베딩 단독과 BM25 단독은 비슷했지만(11승 11패) 잘하는 질의가 달라, **둘을 합쳤을 때 가장 좋았습니다** → 앱에 하이브리드 적용.

**질의 예시** (✓ = 정답)

| 질의 | 이름 키워드 상위 | BM25 + 임베딩 상위 |
| --- | --- | --- |
| 옛날 돈과 은행 이야기 | 한국은행 화폐박물관 ✓ · 세종이야기 충무공이야기 · 내 친구 서울 서울갤러리 | 한국은행 화폐박물관 ✓ · 세종이야기 충무공이야기 · 한국금융사박물관 ✓ |
| 전통 술 만들기나 맛보기 | 전주전통한지원 · 전주 전통술박물관 ✓ · 한국전통문화전당 | 전주일몽 ✓ · 모주체험 여 ✓ · 전주 초코파이 체험장 |

**평가의 한계 (발표 때 함께 밝힐 것)**

- 질의 24개·두 지역의 작은 평가셋입니다.
- 정답 라벨은 초안(관광공사 소개글 기준)이며 팀 검토 후 확정합니다. 라벨을 고치면 `npm run eval:recommend` 로 숫자가 다시 계산됩니다.
- 앱에서는 이 점수 단독이 아니라 거리·분류·접근성 조건과 함께 쓰입니다.

## 4. 시연 장면 (실제 키로 확인한 예)

전주 한옥마을, 기타 입력 **"전통 술 빚기, 판소리"**

- 이름에 '술 빚기'·'판소리'가 들어간 장소는 없음 → 키워드 방식은 못 찾음
- 의미 추천 결과: **전주 전통술박물관**, **전주한벽문화관**(공연·전시 복합문화공간)이 일정에 들어가고
  카드에 "추천 이유 · 소개글이 취향과 비슷"이 표시됨
- 화면 안내: "기타로 적은 '전통 술 빚기', '판소리'이(가) 이름에 들어간 곳은 없어, 소개글 뜻이 가까운 곳으로 찾았어요."
